# 設計判断の経緯

このプロジェクトで「なぜこうなっているか」を残しておくためのドキュメント。後から「なんでこの形なんだっけ?」となったときに参照する。

## 全体方針

### なぜ単一 HTML ファイルなのか

ユーザー(オーナー)はプログラミング・開発環境の専門知識がほぼ無い。最初は Claude Code 中心で進めたかったが、Git・サーバー・ビルドツールなどの障壁が高かった。

そこで「単一 HTML ファイルで完結し、ブラウザだけで動く」構成を選択。クラウド配信は GitHub + GitHub Pages の組み合わせで実現。サーバー不要、ビルド不要、依存関係なし。

将来的に複雑化したら見直す可能性はあるが、現在の規模では十分機能する。

### なぜ画像だけ別ファイル(`images/`)なのか

「単一 HTML」の理想と現実の妥協点。

- すべて HTML に Base64 で埋め込むと、ファイルが数 MB になり、編集も困難になる
- キャラクター画像はバイナリで容量が大きい
- GitHub にファイルとして置けば、画像だけの差し替え・追加も簡単

「コードは 1 ファイル、画像は別」という割り切り。

### なぜ Gemini API なのか(他の選択肢ではなく)

- 無料枠が広く、家族での利用や配布に向く
- ユーザー(オーナー)が既にアカウントを持っていた
- 日本語の自然な対話が可能
- ブラウザから直接 fetch で呼べる(SDK 不要)

将来 Anthropic API や OpenAI API への切替が必要になっても、`callGemini` 関数を差し替えるだけで対応可能な設計。

### なぜ API キーをユーザー入力方式にしたのか

GitHub Public リポジトリで公開しているため、コードに API キーを埋め込むと漏洩する。漏洩すると他人に API を使われて課金される。

そこで「各ユーザーが自分の API キーを Google AI Studio で取得し、アプリの設定画面で入力 → LocalStorage に保存」という方式を採用。多少の手間はあるが、安全。

将来サーバーを立てて中継する案もあるが、現段階ではユーザー数も少なく、運用コストの方が問題。

## キャラクター機能の判断

### なぜ最初から 2 キャラなのか

ユーザーの希望(子供 2 人で使うため、それぞれ好きなキャラを選べるよう)。データ構造は最初から N キャラ前提で作られているので、3 人目以降の追加も容易。

### なぜ表情切替方式に `[[EMOTION:xxx]]` タグを使うのか

検討した代替案:

1. **ユーザーが手動で表情を選ぶ** — 自然な体験にならない
2. **AI が JSON 構造化レスポンスで返す** — Gemini の structured output は使えるが、対話の流れが崩れやすい
3. **別 API 呼び出しで感情分析** — コスト 2 倍 + 遅延
4. **タグ方式(採用)** — シンプル、コスト追加なし、テキストレスポンスから抽出するだけ

タグ方式の弱点は「AI がタグを忘れる」こと。これはシステムプロンプトで強く指示することで対応(現状 9 割方は機能している)。タグを忘れたら表情はデフォルト(`munch`)になるだけなので壊滅的ではない。

### なぜキャラごとに履歴を分けるのか

別キャラと話した会話が混ざっていると違和感が強い。「ミルとはこの話をした、プイとはこっちの話」という記憶の分離は、キャラクター性を保つために重要。

LocalStorage は容量が緩い(数 MB)ので、複数キャラで履歴を持っても当面問題ない。

## ユーザーパーソナライズの方針

(まだ実装していないが、設計方針はある)

### 検討した構造

```
第 1 層: 生の対話ログ        — 全会話そのまま保存
第 2 層: 構造化ファクト      — AI が抽出した「ユーザーに関する事実」JSON
第 3 層: 性格・関係性の要約  — プロンプトに毎回含める
```

### キャラ間でプロフィールを共有するか

**共有する**方針。「同じユーザーを複数キャラが知っている」という世界観。ミルとプイで違うユーザー像になるのは違和感がある。

ただし、キャラごとに「そのユーザーとの関係性メモ」を別途持つことは検討価値あり(将来)。

### AI による自動整理機能

ユーザーが自由記述でプロフィール情報を書くと、AI が既存プロフィールと突き合わせて構造化 JSON を返す。これを LocalStorage にマージ保存。

抽出のタイミングは「ユーザーが手動で更新ボタンを押したとき」を基本とする。毎ターン抽出は API コスト的に重い。

## スケジュール機能の方針

(まだ実装していない)

### 外部連携を諦めた理由

検討初期に Google カレンダー連携を希望されたが、以下の理由で「アプリ内完結」に方針転換:

- OAuth 認証には事前のアプリ登録(リダイレクト URL 固定)が必要 — GitHub Pages の URL は使えるが、複雑
- 単一 HTML ファイルでセキュアに OAuth トークンを管理するのは難しい
- 書き込み(予定追加)は 1 ファイル HTML ではほぼ不可能
- 読み取り専用の iCal 連携は将来的に検討の余地あり(公開カレンダー URL を読み込む程度)

### AI による予定自動登録

「明日の 14 時に歯医者」のような自然言語入力から AI が JSON で予定情報を返し、自動で登録する仕組み。これは表情タグと同じ仕組み(`[[ACTION:ADD_SCHEDULE]]{...}[[/ACTION]]`)で実現する想定。

## UI / UX の判断

### iOS 風デザインを採用した理由

- 主な利用環境が iPhone Safari
- ユーザーが iOS の挙動に慣れている
- システムフォント、ぼかし背景、滑らかなアニメーションなどが Safari と相性が良い

### ダークモード対応

`prefers-color-scheme` メディアクエリで自動切替。手動切替ボタンは現状なし(必要になれば追加)。

### キャラクター画像の扱い

- 大きく表示(120px) → タップで拡大表示
- 表情変化のたびに画像を差し替え
- フォールバック: 画像読み込み失敗時は絵文字 🐹 を表示

## 過去に検討して却下した案

### Claude Code 中心の開発フロー(初期構想)

最初は「PC のローカルにリポジトリをクローン → Claude Code で開発 → コミット & プッシュ」という流れを想定したが、Git 環境構築のハードルが高かった。

→ 「claude.ai でコード生成 → GitHub Web UI で貼り付け」という、ブラウザだけで完結するフローに切替。

→ さらに後、ある程度ファイルが揃ったタイミングで「Claude Code で直接 GitHub を編集する」フローに移行(今ここ)。

### IndexedDB の採用

LocalStorage の容量(数 MB)で当面足りる見込みなので採用見送り。将来チャット履歴が膨大になったら再検討。

### サーバーを立てる案

メリット: API キー隠蔽、ユーザー間でのデータ共有
デメリット: 運用コスト、複雑化、ユーザーの管理負荷

現状は個人利用が中心なので、サーバーを立てるメリットがコストを上回らない。

### キャラクターの絵文字代用

最初の検討では「絵文字でスタートして後で画像に差し替え」案も出たが、ユーザーが既にキャラクターデザインシート(モルモット 2 種)を用意していたため、最初から画像を使う方針になった。
